# Decisions for Go observability and resilience reviews

Read the relevant sections when a judgment is contested or context-sensitive. These are decision aids for this skill, not requirements for every project. Verify version-sensitive behavior against primary documentation, the project's declared support, and its actual build/runtime configuration.

## Logs and correlation

- `log/slog` has structured text and JSON handlers, context-aware calls, `LevelVar`, and `LogValuer`. Neither JSON nor a runtime log-level endpoint is mandatory. A project's existing logger may already satisfy its operational contract. `InfoContext` passes context to a handler; it does **not** automatically emit trace IDs. Check the handler, bridge, or request-scoped logger before claiming correlation. `Logger.With` can attach stable request attributes. See [slog](https://pkg.go.dev/log/slog).
- `LogValuer` can redact a value logged through `slog`, but does not protect strings, alternate serialization paths, other loggers, or individual sensitive fields passed separately. Redact or omit data at the emission boundary and verify actual output. `slog.LogAttrs` can reduce allocations for measured hot paths; typed attributes alone are not a promise of zero allocation. See [slog: attributes and values](https://pkg.go.dev/log/slog#hdr-Attrs_and_Values).
- Trace IDs are useful when logs and traces are both available and the IDs can be correlated through the configured pipeline. Avoid a rigid requirement for top-level JSON fields or W3C IDs in every log line. The OpenTelemetry Go SDK currently lists traces and metrics as stable and logs as release candidate; its status can change, so check current documentation before prescribing a logging bridge. See [OpenTelemetry Go](https://opentelemetry.io/docs/languages/go/) and [OpenTelemetry logs](https://opentelemetry.io/docs/concepts/signals/logs/).

## Metrics and tracing

- Request rate, errors, and duration can help a service; queue depth, throughput, freshness, or completion failures may matter more for a worker or CLI. Pick signals from user-visible behavior and operational decisions, not a universal RED/USE checklist. A library may expose hooks or return useful errors instead of publishing its own metrics. See [Prometheus instrumentation practices](https://prometheus.io/docs/practices/instrumentation/).
- Counters, gauges, and histograms answer different questions. Histogram bucket boundaries should support the latency thresholds and aggregation the project needs; default buckets are not automatically defective. Series cardinality grows chiefly with label combinations and, for histograms, the number of buckets. User IDs, raw URLs, trace IDs, or request IDs are usually poor metric labels. See [Prometheus instrumentation practices](https://prometheus.io/docs/practices/instrumentation/) and [Histograms and summaries](https://prometheus.io/docs/practices/histograms/).
- Inspect exporter behavior if the changed code sends telemetry synchronously. A telemetry backend outage should not unexpectedly block user work or create an unbounded queue; a deliberate audit-log durability contract is a different case. Trace sampling can leave a valid trace ID in a log with no stored trace, so that observation alone does not prove propagation failure. See [OpenTelemetry Go sampling](https://opentelemetry.io/docs/languages/go/sampling/) and [OpenTelemetry Go exporters](https://opentelemetry.io/docs/languages/go/exporters/).
- Use the project's tracing and propagator configuration at actual remote boundaries. OpenTelemetry HTTP/gRPC instrumentation is one implementation, not the only valid one; check whether inbound and outbound middleware already propagate context before asking for manual headers or spans. Start manual spans for meaningful operations; end them, and record errors or status according to the instrumentation's semantics. A high-cardinality identifier can be useful on an individual span, unlike a metric label; judge retention cost and privacy rather than banning it categorically. See [OpenTelemetry Go instrumentation](https://opentelemetry.io/docs/languages/go/instrumentation/) and [W3C Trace Context](https://www.w3.org/TR/trace-context/).

## Time budgets, retries, and isolation

- An outbound call should have an appropriate bound from the caller's context, a client or transport timeout, or both. Do not prescribe a single duration for all calls. Check whether cancellation reaches database drivers and remote SDKs; a `Context` argument enables cancellation but does not prove a driver stops immediately. See [Go context](https://pkg.go.dev/context), [HTTP client](https://pkg.go.dev/net/http#Client), and [canceling database operations](https://go.dev/doc/database/cancel-operations).
- Retry only failures that are plausibly transient and operations that are safe to repeat, within the caller's total deadline and a bounded attempt budget. Honor relevant server retry guidance; cancel waits with context; avoid multiplying attempts when SDKs or upstream layers already retry. Backoff with jitter helps prevent synchronized overload, but Full Jitter is one valid strategy, not a universal formula. A circuit breaker is justified when persistent downstream failure would otherwise consume scarce resources and simpler timeouts or concurrency limits are insufficient. If one exists, inspect how it scopes a dependency, counts failures, permits recovery probes, reports state, and avoids opening on caller cancellations or normal business errors. See [AWS Builders' Library: timeouts, retries, and backoff with jitter](https://aws.amazon.com/builders-library/timeouts-retries-and-backoff-with-jitter/) and [AWS Well-Architected: control retry calls](https://docs.aws.amazon.com/wellarchitected/latest/reliability-pillar/rel_mitigate_interaction_failure_limit_retries.html).
- `POST` and `PATCH` are not automatically non-idempotent, nor does every mutation require an `Idempotency-Key` header. When a side-effecting operation is retried after an ambiguous result, inspect the actual idempotency contract: stable operation identity, duplicate handling, result retention, and concurrent-request behavior. An idempotency key is one mechanism. See [AWS Builders' Library: making retries safe with idempotent APIs](https://aws.amazon.com/builders-library/making-retries-safe-with-idempotent-APIs/).
- Bound concurrency and queues where overload is credible. Prefer a clearly owned admission point and release path; do not add a semaphore solely because a service exists. HTTP `429` communicates rate limiting and `503` can communicate temporary unavailability; choose based on the contract and include useful retry guidance where appropriate. A built-in Go `net/http` server already recovers panics from its handler goroutines, logs a stack to its error log, and closes the connection or resets the stream, so a missing custom recovery middleware is not evidence that a handler panic crashes the process or leaves no stack trace. Recovery middleware can still give a stable error response and application-specific telemetry. When such middleware is removed, explicitly identify the change from the prior response to connection close or stream reset. Determine whether clients depend on the prior response before treating removal as acceptable; if that material contract cannot be established and no defect is confirmed, return Insufficient evidence and name the needed client/policy evidence. Other goroutines and transports need separate analysis. See [`net/http.Handler`](https://pkg.go.dev/net/http#Handler), [RFC 6585: 429](https://www.rfc-editor.org/rfc/rfc6585#section-4), and [RFC 9110: 503](https://www.rfc-editor.org/rfc/rfc9110#section-15.6.4).

- For queues and background workers, distinguish receiving, acknowledging, processing, and durably recording completion. Acknowledging before fallible work can defeat a promised redelivery contract. Retrying after a lost acknowledgment may duplicate effects; verify the broker and handler contract before prescribing an outbox or exactly-once mechanism. Fallbacks must preserve stated correctness and freshness requirements, and must not silently turn a failed operation into success.

## Probes and shutdown

- Kubernetes has optional liveness, readiness, and startup probes; `/livez`, `/readyz`, and `/startupz` are naming conventions, not required paths. Liveness should identify a process that needs restarting, avoiding fragile remote checks that create restart loops. Readiness asks whether this instance should receive traffic; a dependency check belongs there only if failure truly makes this instance unable to serve and the check is cheap and bounded. A startup probe helps when startup can exceed a sensible liveness window. See [Kubernetes probes](https://kubernetes.io/docs/concepts/workloads/pods/probes/).
- A service should coordinate stopping new work and draining owned work within its environment's grace budget. Do not require a fixed 3–5 second readiness sleep: endpoint propagation varies and the delay consumes the same termination grace period as the drain. Check actual routing, pre-stop hooks, and the budget before recommending a delay. `http.Server.Shutdown` closes listeners and waits for normal active connections, but does not wait for hijacked connections such as WebSockets; those need separate ownership. Wait for `Shutdown` to return before process exit. Flush buffered telemetry only when that provider requires it and within the remaining budget. See [`http.Server.Shutdown`](https://pkg.go.dev/net/http#Server.Shutdown), [Kubernetes Pod termination](https://kubernetes.io/docs/concepts/workloads/pods/pod-lifecycle/#pod-termination), and [Kubernetes lifecycle hooks](https://kubernetes.io/docs/concepts/containers/container-lifecycle-hooks/).

## Example review distinction

A payment client retries a timed-out `POST` three times around an SDK that already retries, using `time.Sleep` after the caller context is canceled. The payment API provides no idempotency guarantee. The root concern is a potentially duplicated side effect with multiplied attempts and no total budget; report it once, with the observed call path. A focused change is to establish retry ownership and idempotency semantics first, then bound eligible retries to the caller deadline and use a cancelable backoff. Do not demand a circuit breaker or a specific `Idempotency-Key` header without evidence that either is the relevant contract.
