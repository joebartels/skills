# Go interfaces and composition

Choose abstractions from actual callers and required variation. Read the affected types, call sites, tests and project contracts; identify who supplies each dependency and who owns its lifetime. Keep the smallest design that satisfies those needs.

Prefer a concrete value or function when it already expresses the dependency. Introduce a small interface for behavior a real consumer needs, rather than mirroring a concrete type merely to mock it. Tests can exercise the real object with controlled inputs or an existing dependency boundary. A package-owned interface is appropriate when the package defines an extension protocol for host implementations. Preserve that coherent protocol instead of relocating or fragmenting it to satisfy a blanket consumer-ownership rule. Returning an interface can also fit a deliberately hidden implementation; returning a concrete pointer is not universal.

Make runtime dependencies visible where configuration, isolation or ownership matters. For example, two instances needing different HTTP policies should use their supplied clients and endpoints, rather than re-read process environment or replace global defaults during operations. Wire those values at the host boundary. Forward the current call's context to blocking work. Distinguish resources the component acquires from resources it borrows; borrowed clients or files remain under their owner's control.

Choose construction from invariants. A useful zero value can remain ready for ordinary use while optional configuration enables additional behavior. Exercise that path as well as configured instances. Use a constructor when required inputs or validation justify one; use options when actual configuration needs warrant their complexity. Neither a dependency nor a new setting automatically requires an interface, constructor, DI framework or functional-options API.

For work that outlives a call, make start, stop, completion and failure observable to its owner. Library construction should not silently take process control through signal handling, exit calls or global registration unless the host contract explicitly delegates it. Decide whether cancellation requests stopping or also waits for completion, and document the difference. Keep independently owned runs independently controllable.

When a host shuts down several started runs, request stopping for all affected runs, then join every one before releasing resources they may still use. An error from one join does not make another run complete. Collect outcomes before returning or aggregating errors. Apply the same rule when setup fails after some work has already started. Check executable examples and README shutdown recipes as carefully as the implementation: an early return in sample code can skip a required join even when the library API is sound. If shutdown has a deadline, define what remains running and which resources still cannot safely be released when it expires.

Verify the changed composition through real use. For periodic work, include a successful callback followed by another invocation; immediate failure and cancellation alone never exercise recurrence. Check the specified scheduling relation and absence of overlap, then termination and error propagation. For shutdown, hold a canceled callback in cleanup and show the owner waits before releasing its resource, including when another run has failed. Check independent operation through an observed callback event or state, rather than an immediate nonblocking read of a newly started waiter. Bound synchronization waits, observe early failures, and arrange cleanup so a regression produces a useful test failure. Use the project's supported Go version for these checks; broader testing strategy belongs outside this skill.

Keep scope with the decision owner: package placement and import direction belong to `go-package-boundaries`; supported consumer compatibility and release migration belong to `go-api-contracts`. Report the chosen dependency and lifetime ownership, the code changed, and the checks actually run. Do not expand an unrelated helper edit into abstraction or lifecycle work.
