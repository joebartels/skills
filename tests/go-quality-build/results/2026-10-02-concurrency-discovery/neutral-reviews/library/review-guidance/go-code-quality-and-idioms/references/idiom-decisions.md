# Decisions for Go code-quality reviews

Read the relevant sections when a judgment is contested or context-sensitive. These are decision aids for this skill, not requirements for every project. Verify version-sensitive behavior against primary documentation, the project's declared support, and its actual build/runtime configuration.

## Errors and control flow

- Ordinary operational failures should be returned or handled deliberately. `panic` is not routine error flow, but it is not limited to startup: impossible internal invariants and tightly contained package-local panic/recover can be justified. A public library should normally convert recoverable failure to an `error`. See [Effective Go: errors](https://go.dev/doc/effective_go#errors) and [Google Go Style Decisions: panic](https://google.github.io/styleguide/go/decisions.html#dont-panic).
- Wrap with `%w` only when callers should inspect and depend on the cause. That choice can make an implementation error part of the API. `%v` retains the error's **text** while preventing unwrapping; it does **not** sanitize sensitive text for a client response. Translate or redact at untrusted boundaries. A function reading a caller-supplied `io.Reader` may reasonably expose its read error; an internal SQL error may not be a stable public contract. See [Working with Errors in Go 1.13](https://go.dev/blog/go1.13-errors).
- Avoid repeated log entries for one failure, but “log and return” is not universally wrong: logging an event with local operational context and returning a distinct signal can be intentional. Inspect who logs upstream before calling it a defect. Likewise, `errors.Join` (Go 1.20+) is useful when multiple causes must remain inspectable; it does not automatically replace a third-party error type whose ordering, formatting, or API matters. See [`errors.Join`](https://pkg.go.dev/errors#Join).
- Early returns commonly clarify the normal path. Do not split cohesive logic or add guard clauses only to satisfy a visual rule. Treat ignored errors, accidental shadowing, and misleading success values as higher-signal issues than superficial nesting. See [Google Go Style Decisions: handle errors and indent error flow](https://google.github.io/styleguide/go/decisions.html#handle-errors).

## Names, comments, and abstractions

- `gofmt` is the mechanical formatting baseline. MixedCaps, short local names, consistent initialisms, and avoiding redundant package prefixes aid readers. `Get` is usually unnecessary for a simple accessor, but may be part of the domain or protocol; `Fetch` or `Compute` can better signal expensive work. Assess the call site, not an isolated identifier. See [Go Code Review Comments](https://go.dev/wiki/CodeReviewComments) and [Google Go Style Decisions: naming](https://google.github.io/styleguide/go/decisions.html#naming).
- Exported names should have useful doc comments, usually beginning with the name. A comment may need to say **what** the API does as well as why, including constraints or edge cases; “only explain why” is too narrow. Missing documentation matters most when a public contract is otherwise unclear. See [Go Doc Comments](https://go.dev/doc/comment).
- Prefer coherent package responsibilities and avoid meaningless catch-all names, but do not require domain packages for every small utility or flag `user.User` merely by spelling. Examine the actual import-site readability and ownership. Interface placement and package boundaries belong primarily to Architecture & Design. See [Package names](https://go.dev/blog/package-names).
- Generics and interfaces should solve a real repetition or contract need. `any` is a predeclared alias for `interface{}` introduced in Go 1.18, not a keyword or automatic reason to rewrite stable code. Go 1.27 permits [generic methods](https://go.dev/doc/go1.27), but interface methods cannot declare type parameters; do not suggest unsupported signatures or generics merely for novelty.

## Values, receivers, and resources

- A nil slice and a non-nil empty slice both have length zero, but they can be observably different (`nil` tests, JSON `null` versus `[]`, API contracts). Prefer the simpler nil declaration when equivalent; do not claim an empty literal necessarily allocates on the heap or penalize it when non-nil is required. See [Go Code Review Comments: declaring empty slices](https://go.dev/wiki/CodeReviewComments#declaring-empty-slices). Preallocation is a performance choice when size is known and relevant, not a universal quality requirement.
- A useful zero value is desirable where it makes the API simpler, but constructors may legitimately establish required invariants. Choose pointer receivers for mutation and copy-sensitive state; value receivers can suit small immutable types. Method sets, interface conformance, and future growth can determine the choice. Avoid copying a mutex after first use. Do not force uniform receivers when semantics require otherwise. See [Google Go Style Decisions: receiver type](https://google.github.io/styleguide/go/decisions.html#receiver-type).
- `defer` runs at function return, so an unbounded loop may retain resources too long. Check acquisition errors before deferring cleanup, scope each iteration when needed, and check `Close` errors when they matter to correctness. `sync.OnceValue` (Go 1.21+) is helpful for one-time lazy values, while resettable caches and custom lifecycle semantics may require another design. Channel capacity and goroutine location are contextual; review ownership and termination in the actual architecture and resilience contracts, not by banning buffered channels or worker-local goroutines. See [Go Code Review Comments: goroutine lifetimes](https://go.dev/wiki/CodeReviewComments#goroutine-lifetimes).

- An interface holding a typed nil pointer is not a nil interface. Trace conversion at error returns and optional dependencies: returning a nil `*ParseError` as `error` can make callers take the failure branch. Return a literal nil on success when that is the contract. See the [Go FAQ on nil errors](https://go.dev/doc/faq#nil_error).

## Modern Go without churn

- Check the file's effective Go version before recommending syntax or APIs. The Go 1.22 per-iteration loop-variable semantics apply to modules declaring `go 1.22` or later (with file constraints able to select a version); a `tt := tt` rebinding can be needed in older modules and is usually just redundant in newer ones. It is not a grade-worthy defect by itself. See [Go 1.22 release notes](https://go.dev/doc/go1.22) and [Fixing For Loops in Go 1.22](https://go.dev/blog/loopvar-preview).
- Newer standard-library features can simplify code when semantics match: `min`/`max` (Go 1.21), integer range (1.22), iterator helpers (1.23), `new(expr)` (1.26), and generic methods (1.27). Do not demand use of the newest syntax. Go 1.27's `encoding/json/v2` has stricter defaults; existing `encoding/json` remains supported, so migration is not an idiom requirement. See [Go 1.27 release notes](https://go.dev/doc/go1.27).
- Go 1.26 rewrote `go fix` with version-aware modernizers; `go fix -diff ./...` previews suggestions without changing files. Suggestions need review for semantic equivalence, especially nil versus empty values, public APIs, and generated code. The Go team explicitly rejected a `slices.Clone` modernization that could change empty-slice behavior. Go 1.27 also makes `go test` run the `stdversion` vet check by default, which can catch standard-library APIs too new for the effective Go version. See [Using go fix to modernize Go code](https://go.dev/blog/gofix) and the [Go 1.27 release notes](https://go.dev/doc/go1.27).
- Table-driven tests and external `_test` packages can be useful, but neither is mandatory. Test strategy and assertions belong primarily to the Testing skill. A style review may mention a local test idiom only when it directly obscures the changed code; avoid double grading.
