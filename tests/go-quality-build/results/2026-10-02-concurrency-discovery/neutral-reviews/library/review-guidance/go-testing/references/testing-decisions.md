# Testing decisions

Read the relevant sections when a judgment is contested or context-sensitive. These are decision aids for this skill, not requirements for every project. Verify version-sensitive behavior against primary documentation, the project's declared support, and its actual build/runtime configuration.

## Test signal and structure

- A test is valuable when it would fail for a plausible regression in the promised behavior. Review assertions, error cases, side effects, and boundaries. Statement coverage identifies unexecuted code; a high percentage does not show that assertions are meaningful. Go supports coverage for package tests and instrumented integration binaries. See [coverage profiling](https://go.dev/doc/build-cover).
- Table-driven tests and named subtests help when cases share setup and differ in inputs or outcomes. Separate tests can be clearer when setup or behavior differs. Names improve diagnosis, but Go does not require a `name` field or `t.Run` for every row. The `give`/`want` field names, `got`/`want` message convention, and `go-cmp` are useful choices, not gradeable requirements. Use `errors.Is`/`As` for promised error identity or type; check plain nil/non-nil or output when that is the actual contract. `t.Fatal` is appropriate whenever this test or subtest cannot continue, not only during setup; within a subtest it need not stop other cases. See [Go table-driven tests](https://go.dev/wiki/TableDrivenTests), [subtests](https://go.dev/blog/subtests), and [`testing`](https://pkg.go.dev/testing).
- External `package foo_test` tests exercise exported behavior as a consumer; same-package `package foo` tests can verify private behavior and support focused diagnostics. Choose based on the contract under test, not a universal package rule. Handwritten fakes, function injection, generated mocks, and real dependencies each have costs; grade whether the chosen double masks a relevant contract or makes the test brittle, not its implementation style.
- Go 1.22 per-iteration loop-variable semantics apply to modules declaring `go 1.22` or later, subject to file version controls; an installed newer compiler does not grant those semantics to older code. `tt := tt` may be needed in older modules and is usually redundant, but harmless, in newer ones. Check actual capture behavior before assigning severity. See [Fixing For Loops in Go 1.22](https://go.dev/blog/loopvar-preview).

## Isolation, resources, and timing

- `t.Helper` improves caller attribution for helper failures. `t.Cleanup` runs after the test and subtests finish, in last-added-first-called order; it is useful for resources created in helpers. `t.TempDir` removes its directory automatically. `t.Context` (Go 1.24+) is canceled just before cleanup callbacks run, so cleanup can wait for goroutines using that context. None of these makes a test isolated if it mutates other shared state. See [`testing`](https://pkg.go.dev/testing).
- `t.Setenv` restores the prior process environment but affects the whole process. Go forbids using it in a parallel test or one with parallel ancestors; it is not parallel-safe. Keep environment-mutating tests serial or inject configuration. `t.Parallel` is an option only when shared fixtures, global state, and child goroutines remain safe. See [`testing.T.Setenv`](https://pkg.go.dev/testing#T.Setenv).
- Build tags, `testing.Short`, separate packages, and CI stages are alternative ways to control expensive integration tests. A local `httptest.Server` is useful for an HTTP boundary; a real dependency may be needed to verify database or broker behavior. A rollback isolates only operations performed through that transaction; it does not roll back writes made through a separate pool, connection, or independent committed transaction. Check setup, teardown, and scope before claiming isolation. See [`database/sql.Tx`](https://pkg.go.dev/database/sql#Tx) and [`httptest`](https://pkg.go.dev/net/http/httptest).
- A fixed `time.Sleep` used to guess when async work finishes is often flaky; a sleep can be valid when elapsed time itself is the behavior. Prefer synchronization, an observable condition with a bounded deadline, or `testing/synctest` for supported in-process time and goroutines. `testing/synctest` became generally available in Go 1.25; it is not a substitute for real external I/O. See [Testing Time](https://go.dev/blog/testing-time) and [`testing/synctest`](https://pkg.go.dev/testing/synctest).
- `go test -race` detects races only in executed paths and has material runtime cost; recommend it for relevant concurrent code and a feasible CI or targeted verification strategy, not every local run. Repeated runs (`-count`) and shuffled order (`-shuffle=on`) can reveal flakes but passing them does not prove independence. See [Go race detector](https://go.dev/doc/articles/race_detector) and [`go help testflag`](https://pkg.go.dev/cmd/go#hdr-Testing_flags).
- Go 1.27 makes `go test` run the `stdversion` vet check by default. A diagnostic about a too-new standard-library symbol may be a compatibility failure under the file's effective Go version, not a failed test assertion. See [Go 1.27 release notes](https://go.dev/doc/go1.27).

- `t.Fatal`/`FailNow` stop the calling goroutine and must be called from the goroutine running the test, not a worker. Send the worker outcome to the test goroutine and make completion/cancellation explicit; otherwise an early worker exit can leave the test waiting forever. See [`testing.T.FailNow`](https://pkg.go.dev/testing#T.FailNow). A leaked shared fixture with no demonstrated important contract loss is normally moderate; missing or misleading verification of an important behavior can be major. Explain the distinction rather than treating every imperfect assertion as major.

## Fuzzing and benchmarks

- Native fuzzing is useful for parsers and other broad, untrusted input spaces when an invariant or round-trip property can be stated. Seed realistic cases; keep the fuzz target deterministic and isolated. A panic-only target can catch crashes but may miss wrong accepted outputs, so assess the claimed property and risk. Do not require fuzzing for every function. See [Go fuzzing](https://go.dev/doc/security/fuzz/).
- For benchmark code, check that the measured loop exercises the intended work and that setup or cleanup does not distort the result. `testing.B.Loop` (Go 1.24+) protects against some compiler elimination and handles timing around the loop; older `b.N` benchmarks remain valid when written carefully. `b.ReportAllocs` can expose allocation costs. Interpretation of a measured regression belongs to Performance, while validity of a benchmark belongs here. See [testing.B.Loop](https://go.dev/blog/testing-b-loop) and [`testing`](https://pkg.go.dev/testing).
- `govulncheck` evaluates reachable known vulnerabilities in dependencies and the standard library; its findings belong to Security. Whether CI runs it belongs to Deployment & Operations. It is not evidence that behavioral tests are good or bad. See [Go vulnerability management](https://go.dev/doc/security/vuln/).
