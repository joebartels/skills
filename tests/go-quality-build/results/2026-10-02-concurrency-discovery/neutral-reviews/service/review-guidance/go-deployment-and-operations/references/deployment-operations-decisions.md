# Decisions for Go deployment and operations reviews

Read the relevant sections when a judgment is contested or context-sensitive. These are decision aids for this skill, not requirements for every project. Verify version-sensitive behavior against primary documentation, the project's declared support, and its actual build/runtime configuration.

## Builds, images, and release artifacts

- Multi-stage builds help omit compilers and source from a runtime image; other build systems can achieve the same separation. A small runtime image is useful only if it supplies the needed native libraries, certificates, time zones, user records, writable paths, and diagnostic route. Distroless `static` includes CA certificates and time-zone data; `base` includes libc for cgo needs. `scratch` supplies none of those files automatically. A `CGO_ENABLED=0` build can simplify a Linux image, but do not turn it off when the program requires native code, or infer that it alone establishes all runtime compatibility. See [Docker multi-stage builds](https://docs.docker.com/build/building/multi-stage/), [distroless base contents](https://github.com/GoogleContainerTools/distroless/blob/main/base/README.md), and [Go 1.27 ports notes](https://go.dev/doc/go1.27#ports).
- Copying `go.mod` and `go.sum` before source may improve layer reuse. Cache mounts or external caches can be better for ephemeral CI builders. Caching is a speed choice, not a correctness or grading requirement; verify that cache use still resolves the intended dependencies. A `.dockerignore` reduces irrelevant context and can prevent accidental inclusion, but it is not a substitute for controlling what the final stage copies. See [Docker cache optimization](https://docs.docker.com/build/cache/optimize/) and [build best practices](https://docs.docker.com/build/building/best-practices/).
- `-trimpath` removes recorded filesystem paths; it does not by itself make builds byte-for-byte reproducible. Linker `-s` and `-w` remove symbol/debug information and may hinder diagnostics; no fixed size saving is assured. Use such flags when artifact size or path disclosure matters enough to justify the trade-off. Keep a way to identify the exact deployed source, dependencies, toolchain, base-image digest, and target platform. Tags are mutable; digest pinning provides a fixed base but needs an update process. See [`go build`](https://pkg.go.dev/cmd/go#hdr-Compile_packages_and_dependencies), [`cmd/link`](https://pkg.go.dev/cmd/link), and [Docker image pinning](https://docs.docker.com/build/building/best-practices/#pin-base-image-versions).
- For libraries, evaluate module tags and Go major-version paths when release behavior changes; no container is required. For CLIs, check intended platform binaries, execution permissions, version identification, and release artifact integrity when applicable. A released module tag should not be moved after publication. See [Go module release workflow](https://go.dev/doc/modules/release-workflow) and [publishing a module](https://go.dev/doc/modules/publishing).

## Secrets, configuration, and CI gates

- Docker `ARG` and `ENV` are inappropriate for build credentials: values can persist in metadata or image contents. BuildKit secret or SSH mounts supply credentials during a build step without making them a normal layer input. Verify both the mount and the commands it runs do not copy or echo the secret into the artifact or logs. Runtime environment variables, mounted files, workload identity, and secret-manager APIs have different exposure and rotation properties; no vendor SDK or RAM-only delivery is mandatory. Kubernetes Secret volumes are backed by tmpfs on the node, but Kubernetes Secrets are not encrypted in etcd by default and access policy still matters. See [Docker build secrets](https://docs.docker.com/build/building/secrets/) and [Kubernetes Secrets](https://kubernetes.io/docs/concepts/configuration/secret/).
- Parse required configuration before accepting work and make invalid values diagnosable without printing credentials. A specific validation library, immutable binary, or environment-variable-only scheme is not required. Check whether a secret or configuration rotation requires a restart, file re-read, or other supported mechanism; an environment variable in a running process does not update merely because its source Secret changed. See [Kubernetes Secrets](https://kubernetes.io/docs/concepts/configuration/secret/).
- CI should run checks relevant to the artifact and risk, using a supported Go toolchain and the same important build tags and targets as the release. `go test`, `go vet`, `govulncheck`, image scanning, signing, SBOMs, and provenance answer different questions; none is a universal checkbox. A green scan does not prove safety. If the release relies on attestations, verify they survive the export path and refer to the shipped image. See [Go vulnerability management](https://go.dev/doc/security/vuln/), [Docker build attestations](https://docs.docker.com/build/metadata/attestations/), and [Go release history](https://go.dev/doc/devel/release).

- Follow the identity of tested source through build and promotion. Testing one commit and later building a moving branch does not establish checks for the shipped artifact. Examine workflow permissions and trust transitions when untrusted pull-request code can run in a job with release credentials; review the actual checkout and execution path. Prefer identifying the verified artifact over merely adding another nominal green job. See [GitHub Actions secure use](https://docs.github.com/en/actions/reference/security/secure-use).

## Probes, termination, and rollout

- Kubernetes liveness asks whether restarting this instance may help; readiness asks whether it should receive traffic; startup probes protect slow initialization. All are optional and may use HTTP, TCP, gRPC, or exec, with platform-specific paths. Avoid brittle remote dependency checks in liveness. A readiness dependency check is useful only if that failure means this instance cannot serve its routed work, and the check is cheap and bounded; an unconditional database ping can make every replica unready during a shared outage. Consider probe periods, timeouts, and failure thresholds before judging a handler alone. See [Kubernetes probes](https://kubernetes.io/docs/concepts/workloads/pods/probes/).
- Kubernetes marks terminating endpoints not ready for normal Service traffic; a fixed `3–5s` sleep after flipping readiness is not a universal requirement and consumes termination grace. Check ingress, endpoint propagation, pre-stop hooks, service mesh, and connection behavior before suggesting any pause. The grace period includes hook execution and application drain. See [Pod termination](https://kubernetes.io/docs/concepts/workloads/pods/pod-lifecycle/#pod-termination) and [endpoint termination flow](https://kubernetes.io/docs/tutorials/services/pods-and-endpoint-termination-flow/).
- `signal.NotifyContext` can cancel owned work on a signal; its `stop` function releases registration and may restore a second interrupt's default behavior. `http.Server.Shutdown` stops listeners and drains normal active connections within its context; the main process must wait for it to return. It does not drain hijacked connections such as WebSockets. Queue consumers and background jobs need their own stop and ownership plan. Match the application's bounded shutdown, any pre-stop or ingress delay, and telemetry flush to the actual grace period, with margin. See [`os/signal.NotifyContext`](https://pkg.go.dev/os/signal#NotifyContext) and [`http.Server.Shutdown`](https://pkg.go.dev/net/http#Server.Shutdown).
- Rollout policy should fit replica count, spare capacity, and compatibility needs. Kubernetes `maxUnavailable`, `maxSurge`, and readiness can control replacement; a progress deadline **reports** a stall but does not automatically roll back. A container rollback may not reverse a database migration or external side effect, so check old/new schema or protocol coexistence when the change requires it. See [Kubernetes Deployments](https://kubernetes.io/docs/concepts/workloads/controllers/deployment/).

## Runtime budgets and diagnostics

- `GOMEMLIMIT` is a soft limit on Go runtime-managed memory, not a cgroup OOM shield. The [Go GC guide](https://go.dev/doc/gc-guide) suggests an additional 5–10% of headroom as a starting point for one Go process in a controlled container; cgo, mapped memory, shared processes, tmpfs, and workload spikes can require more. Compare with actual memory and GC/CPU behavior. An absent `GOMEMLIMIT` is not automatically a defect, and `80–90%` is not a universal target. Kubernetes memory limits can still cause OOM kills. See [Kubernetes resource management](https://kubernetes.io/docs/concepts/configuration/manage-resources-containers/).
- Container platforms commonly collect stdout/stderr, but log format and routing depend on the configured driver or collector. JSON, `slog.LevelVar`, or a dynamic log-level endpoint is not mandatory. Ensure logs are retrievable and bounded; Docker's default `json-file` driver may need rotation to avoid disk exhaustion. `pprof` or other admin endpoints should be accessible to intended operators without unintended public exposure; treat an actual exploit path as Security's primary finding. See [Docker logging drivers](https://docs.docker.com/engine/logging/configure/) and [`net/http/pprof`](https://pkg.go.dev/net/http/pprof).
