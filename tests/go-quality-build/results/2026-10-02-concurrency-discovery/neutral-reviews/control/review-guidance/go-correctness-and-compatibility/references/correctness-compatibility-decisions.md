# Decisions for Go correctness and compatibility reviews

Read the relevant sections when a judgment is contested or context-sensitive. These are decision aids for this skill, not requirements for every project. Verify version-sensitive behavior against primary documentation, the project's declared support, and its actual build/runtime configuration.

## Establish the contract before claiming breakage

- Prefer an explicit specification, exported documentation, protocol or schema, and supported release policy. Inspect existing callers and tests for how the contract is used. Tests and observed old behavior can reveal expectations, but neither alone proves that an accidental behavior was promised. If the project intentionally changes a contract, assess the versioning and migration path rather than requiring perpetual preservation of a bug.
- The [Go 1 compatibility promise](https://go.dev/doc/go1compat) describes the Go language and standard library; it does not automatically impose the same promise on every third-party module. For a public module, check its stated policy and tags. The [Go module version guide](https://go.dev/doc/modules/version-numbers) describes v0 and prerelease instability and the usual compatibility signal of v1+ minor and patch releases.
- Source compatibility is broader than unchanged call syntax. A function changed from `func Run(string)` to `func Run(string, ...Option)` can still be called as `Run("x")` while breaking assignments to a `func(string)` variable. Adding a method to an exported interface can break external implementers. Compare real consumer uses or build representative ones. See the Go team's [module compatibility guidance](https://go.dev/blog/module-compatibility).

## Observable behavior and ownership

- Relevant contracts can include stable ordering, nil versus empty JSON, error identity, partial-result behavior, CLI output and exit codes, HTTP or RPC payloads, and persisted representation. Report a difference only when supported consumers can observe it and the old behavior was promised or reasonably relied on under the project's policy. Architecture owns whether the contract was well designed; this review owns whether the implementation keeps it.
- A full slice expression such as `s[:len(s):len(s)]` limits capacity but still shares existing elements. If callers may mutate a returned slice independently, it must be copied (for example with [`slices.Clone`](https://pkg.go.dev/slices#Clone)); a copy is not required when shared ownership is the intended contract. A shallow clone also does not deep-copy referenced elements.
- A nil slice and a non-nil empty slice both have length zero, but they can differ in serialization and explicit nil checks. Judge the actual boundary and documented expectation. Integer narrowing, overflow, rounding, and float comparison deserve a finding when a supported input reaches an incorrect result, not as generic bans.
- A multi-step operation needs rollback or atomic storage only if its promised outcome requires all-or-nothing behavior. Establish where commits, acknowledgments, or durable writes occur before reporting lost work or false success. Do not infer exactly-once delivery, idempotency, or transactionality from a function name alone.

- Successful iteration is not necessarily complete I/O. Check errors after `Rows.Next` or `Scanner.Scan` stops, partial read/write outcomes, and flush/close errors when the contract depends on completion or durability. For `io.Reader`, process returned bytes even when the same call returns an error. Report the actual partial-success path rather than imposing transactionality on every loop. See [`database/sql.Rows.Err`](https://pkg.go.dev/database/sql#Rows.Err), [`bufio.Scanner.Err`](https://pkg.go.dev/bufio#Scanner.Err), and [`io.Reader`](https://pkg.go.dev/io#Reader).

## Concurrency and version claims

- A race or deadlock finding needs a reachable concurrent use path. A [`go test -race` run](https://go.dev/doc/articles/race_detector) can confirm an exercised race, but a clean run does not prove all paths safe. Code inspection may establish shared unsynchronized mutation even when the detector cannot exercise it. Describe the observable risk without escalating every possible race to critical severity.
- A module's `go` directive and any version-implying file build constraint determine language semantics for a source file; a newer compiler alone does not grant every newer language feature. Check the [Go toolchain documentation](https://go.dev/doc/toolchain) and the effective build target before recommending a fix or claiming a compatibility failure. Distinguish a deliberate minimum-version bump from an accidental use of an unsupported feature. Dependency and toolchain upgrade policy belongs primarily to Dependencies & Reproducibility.
