# Decisions for Go performance and resource reviews

Read the relevant sections when a judgment is contested or context-sensitive. These are decision aids for this skill, not requirements for every project. Verify version-sensitive behavior against primary documentation, the project's declared support, and its actual build/runtime configuration.

## Measurement before tuning

- Establish a baseline and a workload that matters to users before claiming a speed or allocation improvement. Compare like for like: same code path, inputs, Go version, architecture, and reasonably stable environment. Repeat noisy benchmarks and use [`benchstat`](https://pkg.go.dev/golang.org/x/perf/cmd/benchstat) when useful; no fixed count such as ten runs proves significance. Include `-benchmem` when allocations matter. Go 1.24 added [`testing.B.Loop`](https://go.dev/blog/testing-b-loop), which avoids several loop and compiler-elision pitfalls; `b.N` remains valid for earlier modules. Setup and teardown belong outside the measured loop unless they are the operation under review. A benchmark's structure is Testing's concern; the speed conclusion is Performance's.
- Use [CPU, heap, allocation, goroutine, block, and mutex profiles](https://pkg.go.dev/net/http/pprof) for the question each can answer. Block and mutex profiles require appropriate sampling to be enabled. Go 1.27 adds a [`goroutineleak` profile](https://go.dev/doc/go1.27) that detects some permanently blocked goroutines, but it cannot find every leak. `go tool trace` is useful for scheduler and blocking behavior; it is not required for every latency concern. Do not promise a universal profiling overhead or insist on continuous profiling. Restrict diagnostic endpoints and collection according to the deployment's security boundary; a public `pprof` endpoint is a Security finding. For long-running services, [`runtime/metrics`](https://pkg.go.dev/runtime/metrics) can help distinguish live heap, runtime-managed memory, and goroutine trends; process RSS, cgo, mapped memory, and container accounting may differ.
- [`go build -gcflags=-m=2`](https://pkg.go.dev/cmd/compile) can explain escape and inlining decisions for a targeted package. Escape to heap is not itself a defect, and the compiler's inlining budget is an implementation detail, not an 80-node code-style limit. Profile and benchmark before splitting readable functions solely for inlining or forcing bounds-check elimination.

## Memory, GC, and reuse

- `GOMEMLIMIT` is a **soft limit on Go runtime-managed memory**, not a container OOM guarantee. It excludes memory such as cgo allocations and some mappings. The [Go GC guide](https://go.dev/doc/gc-guide) suggests 5–10% headroom as a starting point when a controlled container mostly runs one Go process; larger external memory or shared workloads need more. A limit near the live heap can cause heavy GC work and still be exceeded. Tune `GOGC` and the limit from observed memory and CPU trade-offs. Do not require a runtime memory limit for a library or a CLI distributed to unknown environments. Container setting and rollout belong to Deployment & Operations; a code-level retention problem remains Performance's.
- Preallocate slices or maps when useful size information exists and growth or rehashing is consequential. Overestimating capacity can waste or retain memory. Value slices may reduce pointer scanning but can increase copying or change identity; pointer slices can be appropriate. Compare costs for the actual element size and access pattern instead of treating one layout as universally faster.
- Allocation costs change with Go releases: [Go 1.27 adds size-specialized allocation paths](https://go.dev/doc/go1.27) for some small objects. Re-run comparisons on the deployed toolchain rather than carrying forward an old per-allocation cost estimate.
- [`sync.Pool`](https://pkg.go.dev/sync#Pool) is a cache of temporary objects for reuse across independent concurrent clients. Items can disappear at any GC; it is not a capacity guarantee or general ownership mechanism. Reset state before reuse, do not access an item after `Put`, and prevent sensitive fields or huge buffers from crossing requests or being retained. Resetting a slice length does not clear backing data or release capacity. A pool is justified when the measured allocation benefit exceeds complexity and retention cost; ordinary allocation is often simpler and fast enough.
- Streaming can bound memory when large data sets would otherwise be materialized. It must preserve ordering, error handling, and resource cleanup. For database rows, close `Rows` and check `Rows.Err()` after iteration; an early return must still release them. See [`database/sql.Rows`](https://pkg.go.dev/database/sql#Rows).

- A cache needs a bound appropriate to what it retains. An entry-count limit does not bound bytes when values vary widely, and TTL does not cap peak growth before expiry. Include live value size, retained backing storage, eviction work, and concurrent fills in the workload analysis. Separate demonstrable retention from optional caching or micro-optimization ideas.

## I/O, pools, and resource ownership

- The [`sql.DB` connection pool defaults](https://go.dev/doc/database/manage-connections) suffice for most programs. `SetMaxOpenConns` can protect a database but also introduces waiting and possible deadlock. More idle connections can reduce reconnect churn, but setting idle equal to open is not a universal optimum; `SetConnMaxIdleTime` and `SetConnMaxLifetime` serve different purposes. Inspect `DB.Stats`, database limits, instance count, and peak demand. A configured number without a workload is not automatically good or bad. Reuse `*sql.DB`; close it when the owning application ends.
- Reuse `http.Client` and `Transport` where connection reuse matters; they are safe for concurrent use. Always close a response body when finished. For HTTP/1.x, reading to EOF can improve reuse, but current [`net/http` documentation](https://pkg.go.dev/net/http#Response) says closing may also drain a conservative amount asynchronously. Unbounded `io.Copy(io.Discard, resp.Body)` can waste bandwidth and time on a huge or streaming response. Fully consume when the content is needed; otherwise make a bounded, workload-aware choice and close. Check `MaxConnsPerHost`, idle settings, protocol, and observed wait/connection churn before tuning transport limits.
- Track ownership of files, sockets, HTTP bodies, database rows, tickers, timers, goroutines, and queues. Closing at the right scope is a correctness and resource concern; `defer` inside a long loop may retain many resources until the outer function returns. Context cancellation controls work only when the blocking API or goroutine observes it. With the newer timer implementation, unreferenced [`time.Timer` and `time.Ticker`](https://pkg.go.dev/time) values can be collected without `Stop`. In Go 1.23–1.26, check the main module version and `GODEBUG=asynctimerchan` because they can select legacy behavior; see [Go 1.23 timer changes](https://go.dev/wiki/Go123Timer). Go 1.27 removes that legacy implementation. Under the newer behavior, use `Stop` when behavior or prompt cancellation requires it, not as an automatic memory-leak fix. Do not assume GC will promptly close non-memory resources. See the [Go GC guide on deterministic cleanup](https://go.dev/doc/gc-guide).

## Concurrency and compiler choices

- Bound in-flight work when realistic load can grow goroutines, queued data, or connection demand beyond capacity. A fixed worker pool, semaphore, bounded channel, caller-provided limit, or synchronous flow may each fit. Check cancellation and completion ownership. Observability & Resilience grades overload behavior and failure containment; Performance grades the supported time or resource cost. Cross-reference the same unbounded queue under one shared finding ID in a combined report.
- Use a mutex, `RWMutex`, atomics, sharding, or reduced shared state based on semantics first. [`RWMutex`](https://pkg.go.dev/sync#RWMutex) is not inherently faster for read-heavy code; write contention, critical-section length, and scheduler behavior matter. Atomics do not automatically simplify a multi-field invariant. Profile contention before adding cache-line padding or lock-free complexity. A hardcoded 64-byte pad may not align the field as intended across targets.
- `unsafe.String` can avoid a copy only under strict lifetime and immutability conditions: the bytes must not change while the string exists. See [`unsafe.String`](https://pkg.go.dev/unsafe#String). A parser returning a string that aliases caller-owned mutable `[]byte` is unsafe; a benchmark gain does not excuse the broken contract. Prefer ordinary conversion or an API that keeps byte ownership explicit. Similar caution applies to manual bounds-check tricks and representation changes; measure benefit on the deployed Go toolchain and verify correctness.
- [PGO](https://go.dev/doc/pgo) is available from Go 1.20 and enabled by default for a main package with `default.pgo` from Go 1.21. Representative CPU profiles can help whole-program performance; the Go team's reported 2–14% was for a benchmark set, not a promised gain for any project. A library cannot independently require downstream programs to build with PGO. Assess profile provenance, build reproducibility, and before/after performance when PGO is in scope; do not mark its absence as a defect.

## Example review distinction

A service reads a ten-gigabyte export with `io.ReadAll` before transforming it, while the deployment has a one-gigabyte memory budget. This is a supported resource finding even without a production profile: the code's memory demand exceeds the stated budget. Recommend bounded streaming and verify output equivalence and peak memory. By contrast, a library appending a dozen items to a slice without a capacity hint is not a performance defect merely because an allocation could be saved.
