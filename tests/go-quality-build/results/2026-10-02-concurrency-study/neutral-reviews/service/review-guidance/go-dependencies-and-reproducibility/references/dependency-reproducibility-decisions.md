# Decisions for Go dependency and reproducibility reviews

Read the relevant sections when a judgment is contested or context-sensitive. These are decision aids for this skill, not requirements for every project. Verify version-sensitive behavior against primary documentation, the project's declared support, and its actual build/runtime configuration.

## Calibrate the grade to demonstrated reach

- A single supported target or standalone consumer that cannot build because of a missing requirement, sum, or compatible toolchain is normally a contained **major** finding: C if it is the only material issue. Two independent such breaks can reach C-. Do not use F merely because the failed target matters.
- A build input that is only used for optional future regeneration can be **moderate** when the shipped build uses committed generated code and no current mismatch is shown: B for one issue. If that uncontrolled input runs in the release build and changes core production code across all artifacts without a recorded identity, its demonstrated reach can be **critical**: F. Check the actual build path and output before escalating.
- Ordinary correct module configuration and supported clean builds can justify A. A+ needs evidence of two separate safeguards beyond normal resolution, such as controlled regeneration plus independent artifact identity verification under a stated audit requirement. Do not award A+ by splitting one ordinary build check into two bullet points.

## Resolve the graph before judging a diff

- `go.mod` requirements plus [minimal version selection](https://go.dev/ref/mod#minimal-version-selection) determine selected module versions. A direct requirement is a minimum, not an isolated lock on all transitive versions. `go.sum` records hashes of module files the command has needed; it can contain multiple versions and is [not a lockfile](https://go.dev/wiki/Modules). Check `go list -m all`, `go mod graph`, or `go mod why -m` in the relevant main-module/workspace context when the effect of a change is unclear. An indirect module can still supply packages to a build, while a test-only import need not be linked into a production binary.
- For v2+ modules, check [semantic import versioning](https://go.dev/ref/mod#major-version-suffixes) when a module path or major version changes; an incompatible suffix or tag can make the intended package unresolvable. Judge the actual selected path and published release policy, not a blanket requirement to upgrade every dependency.
- `go mod tidy` adjusts `go.mod` and `go.sum` for imports including relevant test and tool packages and considers build tags broadly; it can expose dependency or Go-version constraints. A tidy diff is neither proof of program correctness nor a defect by itself. On a supporting toolchain, `go mod tidy -diff` shows needed edits without writing them. Avoid calling an absent `go.sum` bad when no external sums are needed, including a standard-library-only module.
- `replace` can point to a versioned fork or a local directory; a local path is legitimate when that directory ships in the intended checkout. Confirm that the replacement is available in the release or consumer context and that the selected code is what maintainers intend. A replacement in the main module or workspace does not become a transitive consumer's replacement merely because a library author used it locally. `exclude` and `retract` affect selection in different ways; inspect the actual selected graph rather than assuming intent from a directive's name.

## Separate workspace, consumer, and release contexts

- A [`go.work` workspace](https://go.dev/ref/mod#workspaces) can substitute local modules and override replacements. That can intentionally support a monorepo, but it can also hide a missing `require` or an unpublished dependency in a module that is released separately. Test the module with `GOWORK=off` when it is meant for standalone consumption. If the repository deliberately builds and ships only as a multi-module workspace, test that actual path too; a committed `go.work` is not automatically wrong.
- `-mod=readonly` rejects required `go.mod` updates and bypasses vendoring; it does not make arbitrary Go commands non-mutating. Module diagnostics can fetch metadata or write sums; `go mod verify` can add missing `go.sum` hashes while loading the graph. Use a disposable copy for those checks and preserve the release build mode. A warm cache or active workspace can mask missing committed requirements or sums; a clean checkout and relevant module cache make the evidence stronger. `go mod verify` checks downloaded module content against hashes in the cache, but does not by itself establish the selected graph, a clean build, or the safety of code. An offline build is required only when the project actually promises one; a proxy-backed clean build can be reproducible without vendoring.
- If [vendoring](https://go.dev/ref/mod#vendoring) is used, check `vendor/modules.txt` and selected packages against `go.mod`. Go may select vendor mode automatically for an eligible main module with `vendor/` present. A stale vendor tree can break a build or silently change what developers think they are testing. Vendoring is an option, not a default grade requirement.

## Distinguish minimum Go version from toolchain preference

- The `go` directive states a minimum Go version and influences language/module behavior. A module's `go` version must be at least its dependencies' declared minimum. A `toolchain` line suggests a toolchain for the main module or workspace; it is not a promise that older local toolchains can accept a higher `go` requirement. [`GOTOOLCHAIN=local`](https://go.dev/doc/toolchain) prevents automatic switching. Check the project's actual support matrix before scoring a version bump. A deliberate, announced support change can be acceptable; a test or generator dependency should not silently remove promised consumers.
- Build tags, `GOOS`/`GOARCH`, `CGO_ENABLED`, C compilers and libraries, and `GOFLAGS` can change selected packages or output. Verify only promised targets. A single passing host build is not evidence for all targets. Where cgo or cross compilation matters, identify the native toolchain and libraries actually used; do not demand cgo-free builds by default.

## Identify controlled and uncontrolled inputs

- [Module authentication](https://go.dev/ref/mod#authenticating) uses `go.sum` and, by default, the public checksum database for public modules. An absent hash may be fetched and recorded when the build mode allows it; a readonly build can fail when a needed sum is absent. For private modules, `GOPRIVATE`, `GONOPROXY`, and `GONOSUMDB` can intentionally bypass public services; check the configured internal access path rather than demand a public checksum-database entry. `GOSUMDB=off` weakens public module authentication, but score it here only for a demonstrated input-control consequence; an exploitable vulnerability is a Security finding.
- A checked-in generated file can make today's build repeatable even if regeneration later uses a floating generator. Grade that future regeneration gap by its actual impact. A generator run during every release build is a stronger risk. Record a usable generator version or equivalent immutable input when repeatable generation is part of the contract; avoid a universal mandate to commit generated output.
- Repeatable dependency resolution, repeatable build success, and bit-for-bit identical artifacts are different claims. Binary identity can depend on exact source, compiler, flags, VCS metadata, paths, timestamps, cgo and packaging. The [Go team's reproducible-build discussion](https://go.dev/blog/rebuild) explains relevant inputs. Require control of those details when the project claims or needs binary identity, not for every ordinary library review. Deployment & Operations grades whether the release pipeline records, promotes, and deploys the intended artifact.
