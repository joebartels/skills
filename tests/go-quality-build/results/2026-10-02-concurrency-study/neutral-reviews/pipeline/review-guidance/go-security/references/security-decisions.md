# Decisions for Go security reviews

Read the relevant sections when a judgment is contested or context-sensitive. These are decision aids for this skill, not requirements for every project. Verify version-sensitive behavior against primary documentation, the project's declared support, and its actual build/runtime configuration.

## Known vulnerabilities and verification

- `govulncheck` is useful for known Go module and standard-library vulnerabilities. Source scans use call-graph analysis under the Go version and build configuration actually scanned; `-tags` and `-test` can change coverage. A binary scan uses symbol information and cannot provide source call stacks. Reflection, `unsafe`, interface calls, binary symbol limits, incomplete advisories, and alternate build configurations can affect results. A clean result does not certify security; a module-level advisory alone does not establish exploitation. Triage the advisory, called symbol, fixed version, affected inputs, and reachable path. See [govulncheck documentation](https://pkg.go.dev/golang.org/x/vuln/cmd/govulncheck) and the [Go vulnerability database](https://go.dev/doc/security/vuln/database).
- Do not require a `govulncheck` CI gate to grade a code path. Security grades an identified vulnerability and its exposure; Deployment & Operations grades scan enforcement. A scanner can be run read-only when already available and relevant. `gosec` or another static analyzer produces leads to inspect; it is not a replacement for a secret scanner or for data-flow review. Never infer absence of vulnerabilities from a tool that was not run or could not cover the build. See [Go security best practices](https://go.dev/doc/security/best-practices).

## Untrusted input, JSON, and resource limits

- Apply request-body limits before buffering or decoding when attacker-sized bodies can consume memory or processing time. `http.MaxBytesReader` is an appropriate HTTP mechanism, but the limit comes from the endpoint's contract, not a universal 1 MB threshold. Consider decompressed size, archive entry count and size, multipart parts, and parser work separately. `ReadHeaderTimeout` is relevant for slow headers; `ReadTimeout`, `WriteTimeout`, and `IdleTimeout` have distinct semantics and should fit streaming and deployment behavior. Do not require all four for every service. See [`MaxBytesReader` and `http.Server`](https://pkg.go.dev/net/http).
- `encoding/json.Decoder.DisallowUnknownFields` rejects unmatched object keys when decoding into a struct. It does not by itself prevent mass assignment: the destination type and later authorization decide which fields may change. A second decode expecting `io.EOF` can reject concatenated JSON values; handle a non-EOF error distinctly rather than treating every result as an extra object. Go 1.27 introduced `encoding/json/v2`, whose defaults reject duplicate object names and invalid UTF-8; the established `encoding/json` API retains compatible v1 behavior. Check the package and effective Go version before recommending migration or relying on either default. Use a dedicated input model when accepted fields differ from stored or privileged fields. See [`encoding/json`](https://pkg.go.dev/encoding/json), [Go 1.27 release notes](https://go.dev/doc/go1.27), and the [v2 migration guide](https://go.dev/doc/jsonv2-migration).
- A struct-validation framework is optional. Validate constraints that protect the operation at its boundary and enforce authorization on the resulting action. Schema validation, gRPC interceptors, and domain constructors may divide responsibilities; inspect their real coverage. Rejecting all unknown input is useful when it prevents ambiguity or unwanted fields, not an automatic security requirement.

## Injection, files, and network destinations

- Bind values as SQL parameters. Identifiers, sort directions, and other SQL syntax usually cannot be parameterized; select them from a fixed allowlist before constructing the query. Determine whether an input can reach SQL syntax, rather than flagging every `fmt.Sprintf` around a query. See [Go database query documentation](https://go.dev/doc/database/querying).
- `filepath.Clean` plus `strings.HasPrefix` is not a safe containment primitive. Prefix checks can mis-handle boundaries, and lexical validation does not stop symlink traversal or time-of-check/time-of-use races. For untrusted relative paths, use `filepath.IsLocal` where available; when an attacker can affect filesystem contents, use traversal-resistant `os.Root` / `os.OpenInRoot` on supported, patched Go versions and choose APIs available to the module. `os.Root.ReadFile` arrived in Go 1.25. Older projects may use an equivalent vetted traversal-resistant API. Check mount, device, and platform assumptions separately. See the Go team's [traversal-resistant file API guide](https://go.dev/blog/osroot), [`os.Root`](https://pkg.go.dev/os#Root), and an [os.Root traversal advisory](https://pkg.go.dev/vuln/GO-2026-4970) illustrating why patch level matters.
- `exec.Command` does not invoke a shell by itself, so separately passed data arguments do not acquire shell metacharacter semantics. It is still unsafe to let an attacker choose the executable, interpret untrusted data as flags, or pass data to a program with its own command language. Avoid `sh -c` with untrusted interpolation; pin the executable, validate or terminate options, and constrain privileges according to the called program. See [`os/exec`](https://pkg.go.dev/os/exec) and [Go path security](https://go.dev/blog/path-security).
- Use `html/template` for trusted HTML templates with untrusted data; it applies contextual escaping. Do not convert untrusted strings to trusted `template.HTML`, `JS`, or related types, or parse attacker-controlled template source. Other output formats and client-side DOM sinks need their own defenses. See [`html/template`](https://pkg.go.dev/html/template).
- For server-side requests to user-influenced destinations, inspect scheme and host policy, all resolved addresses, redirects, and the actual dial path. A hostname check before a later DNS lookup can be bypassed by rebinding; an accepted initial URL can redirect to an internal target. When business needs only known peers, an allowlist and fixed request construction are simpler. See [OWASP SSRF prevention](https://cheatsheetseries.owasp.org/cheatsheets/Server_Side_Request_Forgery_Prevention_Cheat_Sheet.html).

## Identity, sessions, and browser credentials

- Authorization is separate from authentication. Trace the subject, object, tenant, action, and ordering of the check. A middleware identity check does not prove object-level permission. Flag a bypass when the protected action is reachable first or through another path. Do not infer a tenant policy from field names alone.
- Prefer a current password-hashing scheme such as Argon2id with parameters chosen for the deployment; bcrypt remains relevant to existing systems and has a 72-byte input limit. Do not impose a universal bcrypt cost of 12. Use the password library's verification function, not `subtle.ConstantTimeCompare` on stored password hashes. For independent secret tokens or MACs, use suitable constant-time verification (for MACs, the MAC API's `Equal`), accounting for encoding and length. See [OWASP Password Storage](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html), [`bcrypt`](https://pkg.go.dev/golang.org/x/crypto/bcrypt), and [`crypto/subtle`](https://pkg.go.dev/crypto/subtle).
- JWT verification must pin allowed algorithms and appropriate keys, verify the signature, and enforce the claims actually required by the relying party: commonly issuer, audience, expiration, not-before, and token purpose. Do not accept `none` for signed-token contracts. Avoid confidential data in merely signed JWT claims. Do not require every claim for every token if the protocol does not use it. See [OWASP JWT guidance](https://cheatsheetseries.owasp.org/cheatsheets/JSON_Web_Token_Cheat_Sheet.html).
- `SameSite` cookies reduce some cross-site requests but usually do not replace CSRF protection for browser-authenticated state changes. Inspect safe-method behavior, Origin or Fetch Metadata policy, anti-CSRF tokens where appropriate, and the trustworthiness of sibling subdomains and proxy headers. Go 1.25 added `http.CrossOriginProtection`; it permits requests without Origin or Fetch Metadata headers, so assess that fallback against the application. CORS configuration alone does not necessarily prevent a cross-site form request. WebSocket handshakes need an origin policy and authentication/authorization appropriate to the channel. See [OWASP CSRF prevention](https://cheatsheetseries.owasp.org/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html) and [`CrossOriginProtection`](https://pkg.go.dev/net/http#CrossOriginProtection).

- Using a standard cryptographic package is not sufficient evidence of safe use. For AEAD encryption, verify nonce uniqueness per key, key lifetime, authenticated metadata where the protocol requires it, and rejection of authentication failures before using plaintext. When changing encryption construction or nonce handling, preserve the stored/wire format or specify its migration, and verify decryption with supported readers as well as nonce uniqueness and tamper rejection. Check TLS verification and any custom verifier against the actual peer identity contract. See [`cipher.AEAD`](https://pkg.go.dev/crypto/cipher#AEAD) and [`tls.Config`](https://pkg.go.dev/crypto/tls#Config). For a dependency fix, verify the selected fixed version and affected behavior with a focused regression check when feasible; a clean advisory scan alone does not establish behavior preservation.

## Secrets, telemetry, and packaging

- Keep actual credentials out of source, tests, build arguments, images, and logs. Environment variables, mounted files, workload identity, and secret managers have different exposure and rotation properties; choose based on runtime threat model. A vendor SDK or RAM-only secret retrieval is not mandatory. If a committed live credential is found, recommend revocation or rotation as well as removal, without quoting its value.
- `slog.LogValuer` redacts a value only when that value travels through `slog`'s value resolution. It does not redact `fmt`, JSON, other loggers, URLs, traces, or separately logged fields. Verify the actual output path and keep high-risk data out at the emission boundary. See [`log/slog`](https://pkg.go.dev/log/slog).
- A small, non-root container can reduce impact, but `scratch`, distroless, and `CGO_ENABLED=0` are choices conditioned on runtime dependencies, certificates, DNS, native libraries, debugging, and target platform. `-trimpath` removes recorded source paths; it alone does not guarantee byte-for-byte reproducibility. Container user, base image, and build pipeline findings belong primarily to Deployment & Operations unless the changed code or artifact creates a concrete security exposure. See [`go build` flags](https://pkg.go.dev/cmd/go#hdr-Compile_packages_and_dependencies) and [Go security best practices](https://go.dev/doc/security/best-practices).

## Example review distinction

A service accepts an untrusted filename and calls `os.ReadFile(filepath.Join(base, filepath.Clean(name)))`. The attacker can place symlinks under `base`. The issue is a reachable filesystem escape, even if a lexical prefix check is added. Recommend a traversal-resistant root-relative open compatible with the module's Go version; grade its impact from the files the process can access. Conversely, a library that receives a trusted path from its caller and documents that trust boundary does not automatically need `os.Root`.
