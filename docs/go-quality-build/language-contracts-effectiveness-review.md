## Content sufficiency and useful procedures

**Error contracts has enough substance for a focused draft.** Its useful procedure starts at the failed operation, lists completion points, follows the error to consumers, decides inspectable identity/type separately from safe public text, and verifies the promised remaining result. That procedure answers choices ordinary wrapping advice leaves open. The backend task illustrates why private backend diagnostics must be translated away while the domain classification remains visible. The reader and writer tasks illustrate caller-owned causes, valid prefixes, single-error identity and genuinely independent finalization failures. The cursor and CSV tasks make terminal iteration and buffered-write completion concrete.

The guidance is conditional where it needs to be: required direct equality survives; `Join(err, nil)` is not automatically equivalent; owned cleanup can still be best-effort; not every diagnostic must be aggregated; success must be a nil error interface. The completion helper is a useful small implementation example. The skill’s last paragraph leaves supported API evolution, lifecycle design, retries and reporting systems with their existing owners. There is some overlap with API contracts, but API asks which promises must survive while this draft explains propagation and representation under those promises. No public error hierarchy or blanket wrapping rule is prescribed.

**Values and zero values also has enough substance, especially around ownership.** Its core procedure inventories references, marks borrowed/shared/owned state and expiration, chooses copying at retention, preserves only promised nilness/topology, and tests mutations in both directions. This is more specific than reminding an author to keep a zero value working. Graph snapshots, nested map/byte state, borrowed producer buffers and method-set checks make that distinction operational. Constructor-required counter state and intentionally borrowed RootView provide counterexamples to universal zero-value, pointer-receiver and deep-copy rules.

The mechanics reference supports the main procedure with concrete traps: a limited-capacity slice still aliases existing elements, shallow clones retain nested references, copying an empty non-nil slice through a nil append can change its representation, pointer method sets differ from automatic address-taking, and a typed-nil pointer in an interface is not a nil interface. The final exact-capacity wording incorporates the earlier documented correction. The reference is technically useful but partially repeats the main text; it is optional reading, not an empirically established source of better outcomes in these trials. Author reports do not establish which reference sections were read.

**Names/docs is appropriately a reference.** Its factual ledger ties units, defaults, ownership, usable failure results and safety/ordering claims to implementation evidence. It explicitly preserves public/protocol names, keeps docs-only work behavioral-neutral, and rejects unrequested naming cleanup or document quotas. These are useful authoring controls, but their strongest facts belong to the API/error/value/composition decision owners. Neither the ordinary casing guidance nor the wide set of Go work that contains names justifies a separately routed skill here. The reference was not independently exposed as an experimental arm and has no behavioral suite; improved documentation elsewhere cannot be attributed to it.

The earlier exact-draft review inspected primary Go sources and ran the examples. Its [archived final checks](../../tests/go-quality-build/results/2026-10-01-language-contracts/draft-review/checks-final.json) show nine semantic/example tests plus vet passing; the [metadata](../../tests/go-quality-build/results/2026-10-01-language-contracts/draft-review/metadata.json) identifies the extracted snippets. ## Reader precedence: reconciliation with the earlier review

The earlier error baseline review already reproduced the relevant behavior but classified it as unresolved precedence: malformed bytes plus a read failure yielded a valid prefix and LineError while hiding the read cause. It explicitly excluded that combination from its A/A claim. Its final-review follow-up correctly warned against reclassifying the ambiguity merely to manufacture a drafting target. That historical assessment must remain visible.

My arm-blinded review reaches a different, explicit contract judgment. The original README says “The caller's reader errors remain inspectable” and requires processing bytes returned alongside an error; it also requires structured malformed-line errors. None of those clauses grants malformed data an exception to read-cause inspection. The word “or” in the description of terminal conditions does not itself specify exclusive precedence. The earlier comparison to the writer’s more explicit aggregation language is a reason for caution, but it does not cancel the reader’s unqualified inspectability promise. This reasoning depends on the supplied contract, not on preferring the candidate that collects more diagnostics.

A fresh disposable original-module check further verified the exact input `"a=1\nbroken"` returned alongside a custom read cause. Original Load returns that cause with no prefix; baseline candidate A supplies the new valid prefix and LineError but now hides the cause. Candidate B retains both. The confirmed change is thus the loss of an existing inspectable cause while implementing the new partial/structured behavior. The code repro and failing/passing output are preserved in the frozen report. F1 is moderate: a contained caller classification/diagnostic promise is lost, while the valid prefix and malformed-line report remain usable.

The parent separately reran the same original/A/B observation; its [raw output](../../tests/go-quality-build/results/2026-10-01-language-contracts/blind-review/root-cofailure-observations.json) confirms cause visibility `true/false/true` and prefix lengths `0/1/1`. These are repeated executions of the same code, not fresh author trials.

A separate [reader-contract adjudication](reader-contract-adjudication.md), completed without arm-map or draft access, independently confirms the same moderate F1 and B/B judgment. Its [probe](../../tests/go-quality-build/results/2026-10-01-language-contracts/reader-adjudication/probe_test.go.txt) and [raw checks](../../tests/go-quality-build/results/2026-10-01-language-contracts/reader-adjudication/verification.json) distinguish representation freedom from permission to discard an already-delivered promised cause, verify both `errors.Is` and `errors.As`, and preserve the earlier report’s explicit exclusion as historical evidence. This additional review resolves the bounded disagreement in favor of F1; it does not create another author outcome or a causal skill result.

This adjudication occurred **after the drafts and their exposure runs**, although the behavior had been observed earlier. It is not a newly discovered pre-draft weakness, a prospectively agreed primary outcome, or proof that the draft caused its absence in the skill-on result. The draft specifically allows the operation’s contract to settle precedence; it does not simply demand universal aggregation. The observed difference is consistent with its producer-to-consumer procedure, but one author pair cannot distinguish that effect from ordinary run variation or existing API guidance.

If the fixture owner later explicitly chooses parse precedence that suppresses the read cause, that is a different contract interpretation and F1 would not count under it. Preserve this sensitivity. Under that alternative interpretation all twelve pairs tie on these code grades; the recommendations below still hold. Do not silently rewrite the frozen outcome or previous review, tighten hidden assertions and call them original requirements, or use this later adjudication as retrospective justification for drafting.

The export limit case remains ungraded for a distinct reason: the task defines a maximum record count but does not explicitly promise inspection of a buffered read failure after that count has been reached. A returns the observed read failure at limit 1; B returns success after publishing one record. Both close once. Likewise zero Counter.Count is intentionally unsupported, so A’s panic versus B’s zero result is not a supported-behavior regression.

## Harm, costs and interaction assessment

No confirmed skill-on code defect was found in the assessed scopes. Both private controls remain small; no external dependency, package split, unrelated public rename, mandatory constructor, changed pointer receiver or borrowed-resource close was introduced. Value copying follows the requested retention/snapshot contracts; default formatting and predicate inspection avoid extra input copies. These are bounded no-observed-harm results, not proof that the skills are harmless on other tasks.

Two modest costs deserve visibility without fabricated grade deductions. Error skill-on CLI code adds exported `ErrInvalidLimit` beyond the required rejection, creating an extra API commitment; no demonstrated caller need was supplied. The draft already says to introduce stable classification only when callers need it, so that reminder did not prevent the extra surface in this run. Value skill-on borrowed-frame code duplicates the acquisition/error/retention loop in Collect and CollectMatching while the baseline delegates once. That is more code to maintain, but no current inconsistency or substantial maintenance harm was demonstrated. Neither observation supports a new broad ban or speculative draft rewrite.

Test/doc differences are mixed. Some skill-on authors add external API checks or actual CLI tests; some baselines already have strong tests. The error skill-on CSV and baseline both need the private probe to exercise a small buffered flush failure. Counting tests, comments or report sections is not a Testing grade or an effectiveness measure. No mutation study, comparative author effort, tokens, latency or allocation benchmark was performed. The measured reading sizes are 614 and 655 words for the mains, with 573 reference words when opened; both main skills together add 1,269 words. Word count is a content-size cost, not measured cognitive or execution cost.

In the combined task, API governs exact signatures/JSON/CLI grammar, errors governs usable prefixes/causes and final status, and values governs Select’s nested independence/nilness. The resulting code implements these without contradictory requirements, extra resource ownership or unsupported concurrency promises. Both baseline and exposure preserve dual read/parse causes and deep snapshots; both publish the valid selected prefix before failure exit. Skill-on additionally reports input failure when output also fails, but that message policy was not mandated and is not an outcome win. The context-qualified single combined case supports no observed incompatibility in this composition, not synergy or a marginal benefit attributable to either individual skill.
